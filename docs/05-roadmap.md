## Phase 3：DRAW_GUESS 模式 — 已完成

- 猜題聊天室 UI（`GuessChatBox`）與事件串接已完成
- 猜題比對邏輯重用 `guessing-engine` 的 `isAnswerMatch`（見 `03-data-model.md`）
- `lib/engine/drawGuessEngine.ts`：抽題（`pickWordOptions`，每輪抽 2 個候選題目）、輪流指定畫圖者（`getNextDrawer`，Fisher-Yates 洗牌決定固定順序）
- `lib/server/roundOrchestrator.ts`：房間狀態機 `lobby → drawing → roundEnd → 下一輪或 finished` 的完整轉換，猜對或時間到都會自動公布答案、停留 5 秒後自動進下一輪
- **選題機制**：畫圖者每輪從 2 個候選題目擇一（`round:chooseWord` 事件），候選題目只私訊給畫圖者本人；計時在候選題目送出當下就開始跑（不是選定題目後才開始），選題期間猶豫也會消耗作答時間；時間到還沒選則自動保底選第一個候選，確保一定有答案可公布
- **計分規則**：猜中者依「猜中當下剩餘時間比例」拿 1~10 分（`computeGuesserPoints`），越早猜中分數越高；猜中的話畫圖者固定加 5 分（`DRAWER_BONUS_POINTS`）；時間到沒人猜中則雙方都不得分，用意是讓畫圖者有動機畫得讓人看得懂
- `stroke:start`／`canvas:clear`／`canvas:undo` 的畫圖權限檢查：比賽進行中、正處於 drawing 階段、是本輪畫圖者本人、且已經選定題目（不是還在選題畫面）才准畫，其餘一律拒絕（含 lobby、選題中、公布答案停留期間）
- 已通過端對端測試（含真實 Socket.io client）：建房 → 開局 → 收到候選題目 → 選題 → 開始計時 → 非畫圖者偷畫被伺服器擋下（未轉發）→ 猜中 → 自動結算搶分／畫圖者獎勵分 → 公布答案並排程下一輪

## Phase 3.6：搶答制重構與畫布體驗細節 — 已完成

- **猜題規則改為搶答制**：一輪不再是「猜中一個人就結束」，而是等「除了畫圖者之外的所有人都猜中」或時間到才結束這一輪；已猜中的人可以繼續留在房間但這一輪不會再被計分

- **畫圖者計分規則調整**：改成「每有一人猜中，畫圖者加 `DRAWER_POINTS_PER_GUESSER`（2）分」，取代原本猜中就固定加 5 分的規則，理由是現在一輪可能有多人猜中，固定分數已經不合理
- **玩家清單顯示下一位**：新增 `RoomSummary.nextDrawerPlayerId`，比賽進行中會在玩家清單標示下一位輪到畫圖的人

- **倒數橫條預留固定高度**：畫布上方的倒數橫條位置改用固定 `minHeight` 容器，橫條出現/消失時版面不再上下跳動
- **換人畫時清空畫布**：新增 `DrawingCanvas` 的 `resetLocal`（只清本機畫面、不廣播事件），每次新一輪開始時呼叫，避免看到上一位畫的殘留內容

## Phase 3.7：移除房主角色、斷線處理策略、複製功能 — 已完成

- **移除房主角色**：`RoomPlayer` 拿掉 `isHost` 欄位，`RoomState` 拿掉 `hostPlayerId`；房間裡任何人都可以觸發「開始遊戲」（仍要求至少 2 人），不再限制只有建立房間的人才能按。前端 `PlayerList` 拿掉「房主」標籤，lobby 疊層的開始按鈕改為所有人可見
- **斷線處理策略**（`lib/server/socketHandlers/room.ts` 的 `handleLeave`）：
  - 房間還在 lobby：離開的人直接從名單移除，房間清空就整個刪除（跟之前行為一致）
  - 比賽進行中或已結束：不整個移除，只標記離線（`connected: false`）——因為分數、輪流順序（`turnOrder`）都還依賴這個 id，整個移除會讓後續輪到這個人畫圖時找不到人，導致那一輪沒人能畫、白白浪費一整輪限時。所有人都離線時才刪除房間釋放記憶體
  - **畫圖者中途離開，該題立即中斷**：偵測到離開的正是目前的畫圖者，直接呼叫 `endRoundAndAdvance` 公布目前為止已經猜中的人拿到的分數（若還沒選題就先保底選一個），不必等逾時
  - 猜題者中途離開：`countGuessers`（判斷「全員猜中」用）只算目前還連線著的人，離線的人不會卡住其他人提前結束這一輪
- **複製功能**：新增 `CopyButton` 元件，lobby 疊層同時提供房間代碼與邀請連結（`window.location.href`）的一鍵複製，用 `navigator.clipboard.writeText`
- 已通過端對端測試：非建立房間的人成功觸發開始遊戲；畫圖者中途斷線後，該輪在遠小於限時秒數的時間內就公布結果並進下一輪（`correctGuesses: []`、`drawerPoints: 0`）

- **釐清一個原本以為是 bug、實測後確認沒問題的行為**：逐輪的「時間到 → 5 秒停留 → 自動下一輪」本來就正常運作
- **整場比賽結束後自動重啟新一場**：原本「比賽結束」畫面是死路，需要離開房間重建才能再玩。現在公布最終名次、停留 5 秒後，自動分數歸零、重新洗牌決定畫圖順序、開始全新一場比賽，不需要任何人手動觸發，房間就這樣一場接一場玩下去

## Phase 3.10：直接貼連結加入房間 — 已完成

- 修正一個真實 bug：透過複製網址、貼到新分頁開啟房間連結（沒有先經過 `/online` 頁面輸入暱稱），畫面會永遠卡在「連線中」。根因不是連線失敗——WebSocket 早就連上了，只是這個分頁的 `sessionStorage` 沒有這個房間的身分資料（暱稱／`playerId`），原本的邏輯是「沒有身分就什麼都不做」，於是永遠不會送出 `room:join`，`room:state` 也永遠不會回來，畫面自然卡住

## Phase 3.11：離線玩家硬刪除、輪流順序即時修正 — 已完成

- **修正真正的根因**：離線玩家中途離開，卻仍會被輪到畫圖。原因是先前版本只在「標記離線」，沒有整個移除——`turnOrder`（固定的輪流順序陣列）在比賽開始那一刻就決定好了，之後有人離線並不會把他從這個陣列拿掉，輪到他時，房間裡根本沒有這個人可以操作畫布，整輪卡住
- **離線玩家一律硬刪除**：不管房間處於 lobby、playing、還是 finished，斷線／主動離開都直接把這個人從名單整個移除（`roomManager.removePlayer`），不再區分「標記離線」與「整個移除」兩種狀態
- 硬刪除同步修正三件事，確保遊戲體驗即時反映最新的人員狀態：
  - **`turnOrder`／`drawerIndex`**：把離開的人從輪流順序陣列中拿掉，並視情況調整目前的索引位置，確保「輪到誰」在陣列變短之後仍然正確對應（不管離開的人排在還沒輪到的位置、或剛好正在畫圖，都正確處理，兩種情境都有端對端測試覆蓋）
  - **`correctGuesses`**：這個人這一輪如果已經猜對，把猜對紀錄一併移除，避免「還需要幾人猜對」的統計把一個不存在的人算進去
  - **玩家列表**：離線的人立刻從清單消失，不再顯示灰階的「已離線」殘影
- **比賽進行中人數不足直接結束**：離線後如果連線人數低於 2 人，比賽玩不下去，直接公布目前分數並結束（不必等到湊不到人猜題才被動卡住）
- 已通過端對端測試（3 人房間，兩種情境）：離線者剛好是第一位畫圖者、正常畫完才離線，後續輪流順序不受影響；離線者排在後面幾輪、還沒輪到就離線，總輪數正確依剩餘人數收斂，且離線者確認完全沒被輪到

**已知取捨（這次改動的副作用，請知悉）**：硬刪除是立即生效的，任何斷線（包含單純重新整理頁面）都會被當成「離開」處理，且不再保留身分——先前版本至少還會保留分數、輪到他時可以重新整理回來（雖然仍會被判定為離開該輪），現在重新整理等於直接被踢出房間、分數歸零式地整個消失，且因為 `playerId` 已經從房間名單中被刪除，重新整理後也無法用原本的 `playerId` 重新綁定回同一個身分，只能當作全新玩家重新加入（若比賽已經開始，甚至無法重新加入）。這是「即時剔除離線玩家」與「容忍短暫斷線重連」兩種設計取向的直接衝突，這次照您的指示採用前者。

## Phase 3.12：離線者未輪到時，該輪直接取消不重複找人代打 — 已完成

- 修正 Phase 3.11 遺留的副作用：離線玩家若排在「還沒輪到」的位置，`turnOrder` 陣列縮短後，`roundCount`（總輪數）沒有跟著減少，導致模數運算繞回陣列開頭，讓已經畫過的人被重複排到後面的輪次（例如 3 人比賽，第 3 位還沒輪到就離線，第 1 位反而被排到「第 3 輪」重畫一次）
- 修正規則，依離開者當下的位置區分兩種情況：
  - 離開的人**還沒輪到**（排在目前輪到的人之後）：他那一輪直接整個取消，總輪數同步減少，不會有人代打
  - 離開的人**已經輪過、或正在輪到**（含中途中斷畫圖的情況）：這一輪已經算進去了，總輪數不變，後面還沒輪到的人依然正常拿到自己的那一輪

## Phase 6.13：動畫時長拉長，降低被系統設定關掉或錯過的機率 — 已完成

- **修法**：拿掉這個殘留的 1 秒基礎延遲，卡片改成幾乎立刻依序淡入（`i * 0.25` 秒，不再疊加額外等待）；外框繞圈發光動畫也跟著調整，改成從「這張卡片自己的進場動畫播完」那一刻才開始（進場延遲 + 0.5 秒＝進場動畫本身的時長），不再是等所有卡片都出現才統一開始

- **精準定位到根因**：`StatusOverlay.tsx` 用 `justifyContent: 'center'` 搭配 `overflowY: 'auto'`——這是一個經典 CSS 陷阱，內容置中＋允許捲動這個組合，當內容比容器高時，內容會向上下兩側對稱溢出，預設捲動位置（scrollTop=0）看到的不是內容最前面，而是被置中邏輯往下推過的一段，導致最上面的圖示跟標題被捲到看不見的地方。視窗越窄、box 高度（依 aspect-ratio 從寬度算出）越小、內容溢出越嚴重，這個問題就越明顯——精準對應使用者截圖裡「650px 寬時內容從連結那行開始顯示、完全看不到圖示跟標題」的現象

## 修正上一輪批次改動引發的兩個新問題

- 使用者截圖回報：作畫中的畫布尺寸突然變得非常大（畫面顯示 1058×1342，遠超過應有的比例），且接龍模式畫布最上方（放題目標籤跟交棒按鈕的區域）完全沒辦法下筆——兩者都跟上一輪的改動直接相關

### 問題 1：畫布在作畫中變得過大

- **根因**：`<canvas>` 是「替換元素」（replaced element），瀏覽器對它有一套特殊規則——當 CSS 的百分比高度（`height:'100%'`）在某個計算時機點解析失敗（例如外層容器的高度是透過 flexbox `align-items:stretch` 動態算出來，不是一開始就給定明確數值），瀏覽器會退回去用 canvas 元素的 `width`／`height`「HTML 屬性」當作原生顯示尺寸；而這兩個屬性現在是乘過 `devicePixelRatio` 的內部像素解析度（上一輪為了修圖片模糊加的），在 DPR=2 的螢幕上就是 CSS 尺寸的兩倍——一旦真的觸發這個備援路徑，畫布顯示出來的大小就會變成正常尺寸的兩三倍，跟截圖裡看到的異常尺寸吻合
- **修法**：`DrawingCanvas.tsx`、`StrokeReplay.tsx` 的 `<canvas>` 元素都從 `width:'100%', height:'100%'` 改成 `position:'absolute', inset:0`——外層容器已經是 `position:'relative'`，`inset:0` 是相對於最近的定位祖先的內距框直接計算，不會經過「父層高度算不出來就退回原生尺寸」這條容易出問題的百分比高度解析路徑
- 已通過：直接檢查編譯後的最終 JS 產物確認 `position:"absolute",inset:0` 已編譯進兩處畫布元件；端對端功能回歸測試確認兩種模式的完整遊戲流程（含畫布筆畫轉發）都沒有受影響

### 問題 2：接龍模式畫布最上方（題目標籤、交棒按鈕）擋住下筆

- **根因**：包裹題目標籤跟交棒按鈕的 wrapper `div` 用 `left:10, right:10` 撐滿了整個上方寬度、靠 `justifyContent:'space-between'` 把兩個子元素分居兩端——視覺上兩者中間是一大片空白，但這個 wrapper 本身沒有排除指標事件，那塊「看起來是空的」區域還是會攔截下方畫布的下筆動作，使用者會發現最上面那一整條完全畫不上去
- **修法**：wrapper 本身加上 `pointerEvents:'none'`，讓它完全不擋事件；實際要能點擊的標籤（雖然標籤本身不需要互動）跟按鈕各自加回 `pointerEvents:'auto'`，兩者互不影響——這是處理「視覺上有間隔、但邏輯上要當同一個群組定位」這種版面時的標準做法
- 已通過：直接檢查編譯後的最終 JS 產物確認 `pointerEvents:"none"` 已編譯進正確位置；端對端功能回歸測試確認接龍模式完整流程沒有受影響
- **測試限制（誠實說明）**：這個環境沒有瀏覽器可以模擬真實的滑鼠/觸控指標事件，`pointerEvents` 這類純 CSS 層面的修正沒辦法用 socket 層級的測試腳本驗證「點下去真的能穿透到畫布」——socket 測試是直接呼叫伺服器事件，不會經過瀏覽器的 DOM／CSS 事件系統。這個修正的原理是標準、廣泛使用的 CSS 技巧（風險低），但麻煩使用者實機驗證一下最上方那條區域現在是不是真的可以下筆

## 上一輪 position:absolute+inset:0 的修正本身有問題，這輪徹底改用 JS 直接控制尺寸

- 已通過：直接檢查編譯後的最終 JS 產物確認兩處 `canvas.style.width` 的賦值都已編譯進最終版本；端對端功能回歸測試涵蓋兩種模式完整流程（含畫布筆畫轉發），確認沒有受影響

## 畫布尺寸真正的根因：量錯對象，拿畫布量自己

- **真正的根因**：`app/globals.css` 的 `body` 有 `display: flex; flex-direction: column`，讓每個頁面最外層的 `<main className="dg-page">` 變成這個 flex 容器裡的一個 flex item。`<main>` 同時有 `margin:'0 auto'`（用來在超過 `maxWidth:1400` 的寬螢幕上置中內容）——這正是問題所在：CSS flexbox 規格裡有一個容易被忽略的行為，只要 flex item 在橫軸方向上有 `margin:auto`，`align-items:stretch`（body 沒有另外設定，用的是預設值）對這個 item 就完全不會生效，item 會退回去用「內容多寬就多寬」（shrink-to-fit）的方式決定自己的寬度，再用那組 auto margin 把自己置中——不會真的撐滿 body 提供的可用寬度。這是好幾輪截圖裡「main 或畫廊容器量到一個遠小於視窗寬度的奇怪數字」的真正原因，只是先前用 Fit to window 縮放模式測試時被誤判成純粹的顯示縮放問題，掩蓋了底下這個真實的 flexbox 機制
- **修法**：在 `globals.css` 的 `.dg-page` class 補上明確的 `width: 100%`——這是全站每個頁面最外層 `<main>` 共用的 class（首頁、`/online`、`/admin`、DRAW_GUESS 房間頁、DRAW_TELEPHONE 房間頁全部都用），代表這個 bug 原本影響的是整個網站的每一頁，不是接龍模式特有的問題，這次一次修好，不是只補接龍模式這一個案例。補上 `width:100%` 後，`<main>` 的橫軸尺寸不再是 `auto`，不會再依賴會被 auto margin 停用的 stretch、或退回內容寬度；`max-width:1400`／`margin:'0 auto'` 這兩個既有設定完全不受影響，超過 1400px 的寬螢幕還是會正確置中，不會變成貼齊左邊或無限變寬

## 修正真實功能性 bug：接龍模式的復原／清空按鈕完全無效

- 使用者回報：接龍模式作畫時，工具列的返回（復原）跟刪除（清空）按鈕都沒有反應
- **根因**：`stroke.ts` 的 `canvas:clear`／`canvas:undo` handler，伺服器內部的筆畫緩衝區（`clearStrokeBuffer`／`buffer.pop()`）在兩種模式下都有正確執行，問題出在「通知客戶端更新畫面」這一步——原本的判斷式 `if (room.settings.mode !== 'DRAW_TELEPHONE') { io.to(joinCode).emit(...) }` 是為了維持接龍模式「作畫過程中除了自己誰都不該即時看到內容」這個既有設計，但用錯了方法：這個判斷式把事件整個包起來，連**畫圖者自己**都一併被排除在外了。DrawingCanvas 的復原／清空是完全事件驅動的（前端的 `onCanvasClear`／`onCanvasUndo` 處理函式，只有在收到對應的 socket 事件時才會真的去清空／復原本地畫布），這個事件在接龍模式下從來沒有送出過，導致伺服器狀態雖然正確更新了，前端畫面卻完全沒反應
- **修法**：拆成兩步——`socket.emit(...)`（只送給發起這個動作的人自己，不管哪個模式都要送，讓自己的畫布正確反映復原/清空結果）＋`socket.to(joinCode).emit(...)`（廣播給房間裡其他人，只有非 DRAW_TELEPHONE 模式才需要），兩者合起來剛好等於原本 DRAW_GUESS 模式 `io.to(joinCode).emit(...)` 的效果（送給包含自己在內的整個房間），DRAW_GUESS 模式的行為完全不變，只有接龍模式從「完全不送」修正成「送給自己、不送給別人」
- **已通過兩項端對端測試，都是真實模擬多人連線與畫圖動作，不是只檢查程式碼邏輯**：
  1. 接龍模式：畫圖者畫一筆、送出復原、送出清空，確認畫圖者自己確實收到了 `canvas:undo`／`canvas:clear` 事件（bug 修好了），同時確認房間裡另外兩位旁觀者都沒有收到這兩個事件（接龍模式「別人看不到正在畫的內容」的原有設計沒有被破壞）
  2. DRAW_GUESS 模式：確認畫圖者跟猜題的另一位玩家都能即時收到復原／清空事件，維持修改前的行為，沒有被這次改動誤傷

## FRAGMENT_DRAW 第五輪使用者回饋（兩項，第二項影響全站所有模式）

### 問題 1：補全者手滑快速移動時，線條會超出切割界線
- 使用者提供截圖直接看得出來：綠色（補全者）的線條確實跨過了黑色虛線邊界
- **真正的根因**：上一輪的修法只處理了「這一個點在禁止範圍內時不畫」，但沒有檢查「上一個點」的狀態——情境是這樣發生的：遊標快速移進禁止範圍（該次移動事件的點被跳過、不畫，但 `lastLocalPointRef` 被更新成這個禁止範圍內的點），下一次移動事件遊標又飄回允許範圍，這時候的邏輯會畫一條「從禁止範圍內的上一個點」連到「允許範圍內的這一個點」的線段——這條連接線必然會貫穿邊界，正是截圖裡看到的狀況
- **修法**：新增一個 ref 追蹤「上一個點是不是也落在允許範圍內」，改成只有「上一個點」跟「這一個點」**都**落在允許範圍內，才真的畫出連接兩點的線段——不管兩端哪一端落在禁止範圍，這一段線就完全跳過（不畫、不記錄、不送出），確保不管遊標移動速度多快、怎麼跨越邊界，畫出來的線永遠不會越界
- 已確認伺服器端原本就有的範圍驗證（防禦不受信任客戶端的最後一道防線）沒有受到這次修改影響，仍正確攔截任何越界的筆畫資料

### 問題 2：作品列表的解析度跟實際作畫有落差（影響全站，不只接龍模式）
- **真正的根因**：`Stroke.width`（畫筆粗細，畫筆工具列滑桿給的 2~24 這個數字）畫的時候直接原封不動送進 `ctx.lineWidth`，完全沒有跟著畫布實際尺寸做任何正規化。DRAW_GUESS／DRAW_TELEPHONE 的畫布寬度上限 900px、FRAGMENT_DRAW 是 1100px，但作品列表／公布畫廊的預覽框只有兩三百 px 寬——同一個粗細數字，在畫的當下（大畫布）看起來合理的比例，回放在小預覽框時，線條相對畫布的比例會變得又粗又糊，精細筆觸（五官、文字細節）被線條本身的粗細吃掉，這正是使用者說的「解析度／精細度有落差」

## FRAGMENT_DRAW 猜題階段重新設計：從「一組一組公布、大家互相等」改成「每人各自依自己節奏推進」

- 使用者需求：所有組別都畫完後進入猜題階段，不需要等某一組全部人都猜完才換下一組，每個人可以依自己的節奏一直接續猜下一題，直到把該猜的組別全部猜完後才等其他人猜完，最後才呈現所有作品
- 這是核心機制的重新設計，涉及伺服器狀態模型、orchestrator 計時邏輯、公開摘要型別、socket 事件型別、客戶端 hook、客戶端畫面全部要跟著調整

### 資料模型
- `FragmentState` 從「全房間共用一個 `activeGuessTeamIndex`」改成「`guessingStarted` 布林值 + 每位玩家各自的猜題起始時間戳 Map（`guessStartedAtByPlayer`）」——不再有「目前公布到第幾組」這種全房間共用的單一進度指標
- 新增 `findNextTeamToGuessForPlayer`：這是整個重新設計的核心，依 `teams` 陣列順序，找出「不是自己組、自己還沒對它留下猜測紀錄」的第一組，不需要另外維護一個「這個人進度到第幾組」的欄位——直接檢查每一組的 `guesses` Map 有沒有這個玩家的紀錄，天生就是「這個人猜過哪些組」的真實紀錄，用它反推下一組要猜誰，不會有額外狀態要同步、不會有跟 `guesses` 本身對不上的風險
- `allConnectedPlayersFinishedGuessing`：猜題階段結束的條件不是「所有組別都被猜過」，是「所有連線中的玩家自己都沒有下一組要猜了」，人數一多，這兩個條件成立的時間點會不一樣（後者通常比較晚，取決於猜最慢的那個人）
- `submitFragmentGuess` 整個改寫：每次送出猜測後回傳 `hasNextTeam`（這個人還有沒有下一組要猜）跟 `allPlayersDone`（是不是所有人都猜完了），呼叫端據此決定要私訊下一組還是觸發公布
- 新增 `finishFragmentGuessingIfAllDone`、`autoSubmitFragmentGuessForPlayer`（逾時代打，直接重用 `submitFragmentGuess` 的邏輯帶入預設文字「（沒有人猜）」，不需要另外寫一份幾乎一樣的程式碼）

### Orchestrator（`fragmentOrchestrator.ts` 整個重寫）
- 計時器從「一個房間一個 `guessTimers`」改成「每位玩家各自獨立的 `playerGuessTimers`」（`房間代碼:玩家id` 當 key）——因為現在每個人進度不同，逾時計時必須各自獨立算，不能共用
- `sendFragmentGuessPhaseToAllEligiblePlayers`：猜題階段開始的那一刻，分別檢查每一位連線中的玩家，各自私訊通知「現在該猜哪一組」——不是廣播同一組給全房間，每個人該猜的第一組可能不一樣
- `afterFragmentGuessSubmit`：某人送出一次猜測後的收尾，如果他還有下一組要猜就私訊通知下一組，如果這一票剛好讓所有人都猜完了就正式觸發公布，廣播完整內容給全房間
- `checkFragmentGuessingAfterRemoval`：猜題階段有人斷線離開時呼叫，重新檢查是不是剩下的人全部都猜完了——不重新檢查的話，可能發生「還差最後一人的猜測，那個人自己先斷線離開，其他人早就都猜完了，卻永遠不會觸發公布」這種房間卡死的邊界情況

### 型別與事件
- `FragmentSummary` 移除 `activeGuessTeamId`／`guessPhaseStartedAt`／`guessedPlayerIds`／`remainingGuessTeams`，新增 `guessingStarted`（猜題階段是否開始）、`playersStillGuessingCount`（還有幾位連線中玩家沒猜完，給畫面顯示整體進度用，不是每個人自己的進度）
- `fragment:guessPhase` 事件移除 `isOwnTeam`——現在這個事件只會私訊給「真的該猜」的那個人，收到就代表這是輪到自己猜的組別，自己組的作品本來就不會被排進自己的猜題序列裡，不再需要額外判斷要不要顯示猜測輸入框

### 客戶端

- 新增「你已經猜完所有作品了，還有 X 人在猜，全部猜完後會公布結果」的等待畫面，利用新的 `playersStillGuessingCount` 顯示整體進度，跟「還在等其他組畫完」的文字區分開來（同樣是 `myTeam.subPhase === 'done'`，但一個是猜題階段還沒開始、一個是猜題階段已經開始但自己已經猜完了，兩種情境文字含意不同）
- `FragmentGuessSection` 移除 `isOwnTeam` 分支邏輯，簡化成收到就一定顯示猜測輸入框

## 兩項使用者回饋：邊界裁切消失、猜題輸入法（IME）bug

### 問題 1：第一位畫畫移動太快時，分割時接近邊界的部分會消失
- **根因**：不是網路傳輸節流遺失資料（`useDrawingSync.ts` 的批次送出機制本身沒問題，本地捕捉到的點最終都會送達伺服器），是 `filterStrokesByHalf` 的裁切演算法本身的限制——原本的版本要求「至少兩個連續點落在同一半」才會畫出一段可見的線；使用者移動太快時，瀏覽器 pointermove 事件的取樣密度跟不上移動速度，靠近切割邊界的地方可能整段只捕捉到 1 個點就跨到另一半去了，這個孤立的單點會被判定「連不成一段可見的線」而整段捨棄，畫面上就是使用者形容的「接近邊界的部分消失」
- **修法**：`filterStrokesByHalf` 加入邊界內插——沿路徑走訪相鄰兩點，如果兩點分屬不同半（代表這一段跨越了切割線），精確算出這兩點之間、剛好落在切割線上的內插點，把它當成這一段的收尾（或開頭），確保不管原始取樣點多稀疏，保留的那一段線都能確實延伸到邊界為止，不會再有「明明畫過那裡、卻完全沒有任何痕跡」的情況
- 已用獨立腳本驗證：快速移動、稀疏取樣的情境正確延伸到邊界（不再消失）；極端的兩點筆畫（整筆只有 2 個點、剛好分屬兩半）也能正確各自延伸到邊界並保留；來回跨越邊界多次的正常情況依然正確拆成多段，各自延伸到邊界
- 額外在真實遊戲流程的端對端測試中，故意送出一條只有 2 個點、橫跨整個畫布的稀疏筆畫，確認伺服器實際處理後，保留的筆畫確實延伸到邊界座標（0.500），不是停在原本取樣點的位置

### 問題 2：猜題階段有 bug——截圖裡的「沒有人猜」其實是沒辦法猜、被系統直接判定成已送出
- 一開始先設計了好幾組端對端測試想重現這個問題（包含 6 人 3 組、各組完成時間刻意錯開、隨機延遲模擬真人操作節奏），但都沒有重現出來——這代表問題不是猜題階段狀態機本身的邏輯錯誤（上一輪的重新設計沒有問題），而是要換個角度找
- 重新檢視截圖裡「大家的猜測」內容，發現一個關鍵線索：「ㄅ」「ㄅˇ」「33」「ˇˇ」這些內容不是完整的詞語，看起來像是**注音輸入法組字過程中的中間片段**——這指向一個經典的前端 IME（輸入法）處理 bug
- **真正的根因**：猜測輸入框的 `onKeyDown` 直接監聽 Enter 鍵觸發送出，完全沒有排除輸入法組字狀態。中文輸入法（注音、拼音、倉頡……任何需要候選字的輸入法）在組字過程中，使用者按 Enter 是為了「確認選字」，不是要送出——沒有排除這個狀態的話，Enter 鍵會被誤判成「使用者要送出」，把還沒組字完成的片段（例如注音符號本身）直接送出，這正好解釋了截圖裡那些不完整的內容；而「沒有人猜」的人，很可能是被這個問題一直打斷、重新輸入好幾次，最終真的拖到 30 秒逾時，被系統自動代打
- **修法**：所有猜測/聊天輸入框的 Enter 判斷都加上 `!e.nativeEvent.isComposing`（瀏覽器原生提供的 IME 組字狀態旗標），組字進行中一律不觸發送出。這是**影響全站的通用 bug**，不是只有 FRAGMENT_DRAW 才有——`GuessChatBox.tsx`（DRAW_GUESS 模式）、`TelephoneRoomView.tsx`（DRAW_TELEPHONE 模式）、`FragmentRoomView.tsx`（FRAGMENT_DRAW 模式）三處猜測輸入框都是同樣的寫法、同樣的問題，全部一併修正
- 額外發現房間頁面「輸入你的暱稱」的輸入框也是同一種寫法（雖然不在使用者這次回報的範圍內，但用中文輸入暱稱時同樣可能被誤觸發送出加入房間），一併修正，避免同一種 bug 在別的地方繼續發生
- 老實說：這是純前端輸入法互動的修正，這個環境沒有瀏覽器、也沒有中文輸入法可以實際操作驗證，沒辦法直接重現「組字被打斷」這個現象、也沒辦法截圖驗證修正後真的正常——這次是靠分析截圖裡猜測內容的字元特徵（不完整的注音符號片段）反推出根因，麻煩實際用注音或拼音輸入法測試後再回饋

## iPhone Safari：拼圖接畫畫布與切割線只佔外框一部分
- 現象（使用者 iPhone 截圖）：水平切割時，虛線落在畫布約 1/3 高度而非正中間，灰色保留區比實際小。
- 推測根因（未能在 WebKit 實測）：畫布外框高度來自 `aspect-ratio: 3/2` 再被 `min-height: 420px` 撐高；WebKit 讓子層 `height:100%` 只解析成 aspect-ratio 算出的較矮高度（寬 345px 約 230px），畫布與切割線因此只佔外框一部分。Chromium 不會發生，沙盒無法重現。
- 修法：`FragmentCanvas`、`StrokeReplay` 外層改為 `position:absolute; inset:0` 填滿父層，不再依賴百分比高度；`.rm-sheet` 補上 `position:relative`。
- 驗證：Chromium 於 390／360 寬度量測畫布與外框一致；三種模式 socket 回歸通過。**iOS Safari 需實機確認。**


## 首頁滑到最底部突然跳出登入視窗
- 根因：首頁頁尾的 `<Link href="/admin">` 在正式環境進入視窗時，Next.js 會自動預取目標頁；`/admin` 受 Basic Auth 保護（`proxy.ts`），預取請求沒帶帳密，收到 401 與 `WWW-Authenticate`，瀏覽器因此彈出登入視窗。
- 重現：以無頭 Chromium 載入首頁並滑到底，觀察到一筆 `401 /admin?_rsc=…`（RSC prefetch）。
- 修法：該連結加上 `prefetch={false}`，只有使用者真的點擊才請求。其餘 `<Link>` 都指向公開頁面（`/`、`/online`），無同類風險。
- 驗證：修正後同樣操作，對 `/admin` 的請求為零。
- 日後新增指向受保護頁面的連結都要加 `prefetch={false}`。

### 修正：iPhone Safari 首頁點「選這個玩法」整頁越點越放大
- 根因（量測確認）：跑馬燈 `.hm-marquee` 寬 104%＋負邊距＋旋轉，使 `body.scrollWidth` 在 390px 視窗下為 399px；iOS Safari 對超出視窗的內容會擴大版面視口，`html/body{overflow-x:hidden}` 擋不住。連點按鈕又被判定為雙擊縮放，放大疊加。
- 修正：跑馬燈改包在 `.hm-marquee-clip`（`overflow-x:clip`）內、寬度 100%；`html{touch-action:manipulation}` 全站停用雙擊縮放；新增 `components/home/ModeCta.tsx`，點擊後 `aria-busy` 鎖定避免連點。
- 驗證：Chromium 觸控模擬 320/360/390/430/768 皆無橫向溢位（scrollWidth＝視窗寬）；iOS 實機需另行確認。
